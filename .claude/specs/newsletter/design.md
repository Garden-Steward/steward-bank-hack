# Account newsletter ownership

The user approved automatic newsletter enrollment for account holders. Phone, preferred name and email are required in new signup. Enrollment is disclosed. A later login, RSVP, check-in or email change must preserve an unsubscribe. Joining does not subscribe anyone to general SMS. Use the app-owned Resend stack; never invoke the legacy Mailchimp helper or claim an external provider subscription was created.

## Grounding

The current NewsletterView is a Beehiiv link, not an app-owned subscriber record. The approved prototype has an issue reading view, archive, authorized organizer editor/preview/test/review-send flow, and preferences. SMS and newsletter preferences are separate. Existing blog storage has draft/publish but no newsletter recipient/delivery owner. Existing project alerts have a different purpose. The email provider sends through Resend and returns simulated:true in EMAIL_DRY_RUN; it currently drops idempotency options and unsubscribe headers, so publication delivery needs a later explicit adapter change. No provider sends happen in this owner unit.

The participation foundation has private verified_contacts (email/SMS, userId, destinationKey, derivationVersion, proofId, verification and revocation) and contact_proofs (raw/delivery values, purpose, consumption and supersession). It has no newsletter fields. New account creation is still disabled. That transaction must persist actual newsletter ownership before reporting account completion.

## Competing shapes

A stores one newsletter boolean on the user. It cannot distinguish account preference from a bounced/complained-about email shared with another identity or remember that a previous email opted out. It also cannot supply a durable disclosure/change receipt. Reject A.

B stores one account preference/subscription, destination suppression, and immutable preference event records. Choose B. The account row preserves opt-out across email changes; the destination row blocks known bad/opted-out email destinations; events explain the actual automatic enrollment or explicit action. This is one owner/service, with native keys and one transaction, not separate writers of subscriber truth.

Architecture exploration is sequential under the recorded host capacity limit. Required independent review uses a finished nonwriter reviewer. No new approval question is needed under the current implementation/autonomy grant.

## First implementation unit

Add three native private types under api::newsletter, no core routers or broad role grants. Draft/publish false and sensitive attributes private. newsletter-subscription has unique userId and receiptId; preference subscribed/unsubscribed; rawEmail and deliveryEmail text; destinationKey, derivationVersion and verifiedContactId; positive revision; enrollment/disclosure version and firstEnrolledAt; optional unsubscribedAt. A row means durable local enrollment, not provider acceptance.

newsletter-suppression has unique derivationVersion/destinationKey; reason user_unsubscribe, hard_bounce, complaint or manual; server time and opaque source key. Never erase suppression through automatic enrollment. Explicit verified resubscription may remove only user_unsubscribe suppression, with a receipt. Provider/manual suppression requires a separate reviewed recovery action and is not cleared by this unit.

newsletter-preference-event has unique sourceKey, actor userId, subscription receipt, action auto_enroll/unsubscribe/resubscribe/contact_change, resulting preference, disclosure version, server time, request digest and applied revision. Command replay returns the current status and the original applied revision; it never presents an old cached subscribed state as current. There are no generic update/delete routes. Events retain no raw contact values. Retention remains part of the account-deletion launch review; this unit creates no cleanup job.

One service exposes ensureAccountSubscription({userId,verifiedContactId,disclosureVersion}), getAccountStatus(userId), setAccountPreference({userId,preference,expectedRevision,requestId}) changeAccountEmail({userId,verifiedContactId,expectedRevision,requestId}) and suppressDestination({derivationVersion,destinationKey,reason,sourceKey}). These are internal boundaries, not public endpoints yet. No caller can supply raw email/destination hashes to account enrollment. Resolve the live email contact owned by that exact user and its consumed, unsuperseded email proof. Refuse SMS-purpose proof or mismatched destination/version/actor. join_identity requires its intent boundActorId to match the account (set during the outer signup transaction before enrollment). profile_email and email_login require proof.actorId to match the account. A proof is consumed and not superseded; expiry after completed verification does not revoke it. Stored raw/delivery values come from that proof. Require the live unblocked account. A changed email does not reset account preference; a revoked mapping is not eligible for delivery.

Use metadata column names and the existing Strapi outer transaction. Acquire the account row lock first, then the subscription row, and resolve the current contact inside the same transaction. PostgreSQL row locks serialize account changes; SQLite's existing one-connection test pool serializes local writes. Native unique keys and onConflict(...).ignore prevent duplicate account rows/events without catching an aborted PostgreSQL transaction. Every mutating action/event is atomic. An outer account-creation rollback removes subscription and receipt as well. Revision checks protect concurrent explicit changes. All explicit account commands share command:<userId>:<requestId>. Check its durable receipt and digest before revision, proof, suppression or mutation. Exact replay returns current status alongside its original appliedRevision and replayed:true; changed operation/input conflicts. No JWT/contact values are cached.

Automatic enrollment inserts a subscription only once. It returns the persisted subscribed/unsubscribed preference plus eligible/suppressed/unverified delivery eligibility. Repeating it changes neither contact nor preference. A still-live old contact cannot rewind a newer email choice. Only changeAccountEmail with expectedRevision/requestId may choose another owned verified email; it writes a contact_change receipt and preserves preference and suppression. A prior suppression makes delivery ineligible even when the account preference is subscribed. Invalid/no email ownership is an explicit failure; do not create a forever-pending subscription placeholder. New signup must have an owned email proof, so this failure rolls its transaction back. Existing phone-only users must verify an email before they become eligible; no blind backfill or legacy audience import.

Unsubscribe records account preference off and inserts destination suppression, then writes one event. Repeat is idempotent. Explicit resubscribe requires current owned verified email, an expected revision and a new requestId; it may clear only user_unsubscribe suppression. It cannot clear complaint/bounce/manual suppression or SMS STOP. suppressDestination accepts only sticky hard_bounce, complaint or manual reasons. All user_unsubscribe changes are owned by the durable account command receipts, so a delayed old unsubscribe cannot recreate a removed row after explicit resubscription. Precedence is manual above complaint above hard_bounce above user_unsubscribe. One conditional native UPSERT upgrades suppression only to a stronger reason and holds its conflicting row through the transaction. A conditional user-only DELETE during resubscribe cannot erase a concurrent sticky upgrade. Unknown account/foreign contact returns a service error with no contact data. Public controllers will map hidden resources to404.

## Remaining coherent newsletter units

Expose authenticated own preferences through GET/PUT /newsletter/preferences, with PUT {preference,expectedRevision,requestId}; no userId body field. Token-only unsubscribe uses GET to display a confirmation and POST to change preference, so link scanning cannot unsubscribe on GET. Use a separate versioned purpose-bound HMAC capability for the opaque subscription receipt; no account/login/contact-proof token can be reused. No token or raw contact values in logs/analytics. Body token is bounded. Frontend confirmation uses no-referrer and no third-party resources. Standard List-Unsubscribe-Post one-click POST is a separate verified endpoint when delivery is implemented.

Public GET /newsletter/issues lists only published snapshots and GET /newsletter/issues/:slug reads one snapshot. Exact issue snapshots contain bounded title/subject, lead story, approved image/link data and selected actual event facts/links at publication. Draft editor and preview are accessible only to configured app newsletter editors, not every logged-in volunteer or every garden manager. Publisher capabilities default closed when no editor identity is configured. The selected global newsletter does not grant one garden manager access to other gardens' private contacts.

Publication and sending are separate explicit actions. Publishing freezes the public issue; review-send shows the actual eligible count for that snapshot. A durable issue/subscription delivery key prevents duplicates. Provider adapter must pass Resend idempotency keys and unsubscribe headers, enforce dry-run, and record simulated/accepted/unknown truthfully. Retry only known-safe outcomes. A final eligibility check excludes unsubscribe, suppression, blocked accounts and revoked email ownership before dispatch. Per-account serialization must cover the final local dispatch claim versus unsubscribe; a request already accepted by the provider cannot be recalled. Signed raw-body provider webhook verification is required before enabling complaint/bounce feedback; duplicate webhook events are idempotent and never weaken suppression. Sender/domain/legacy suppression carryover and live deployment remain unverified maintainer launch checks, not inferred from local keys. No live send in unattended work.

## Files, tests and rollout

First unit touches three schema.json files, one newsletter service, tests/newsletter-owner.test.js, and .claude/specs/newsletter/design.md. No seed change or current preview backend swap. Use synthetic users, actual private verified contacts/consumed proofs in disposable SQLite/PostgreSQL. Tests must prove automatic enrollment, duplicate/concurrent enrollment, exact raw value round trips, invalid or foreign/revoked/SMS proof refusal, outer rollback, automatic replay never resurrecting opt-out, email change preserving opt-out, revision/idempotency conflict behavior and suppression precedence. Full required pipeline and independent source/comment review gate each checkpoint. The live3031/1342/original stack remains untouched. New registration capability stays off until it calls this real owner transactionally.

Design review reconciliation. The independent review is .audit/run-26/newsletter-design-review.md. Its email rewind, proof binding, command replay ordering and suppression replay findings are incorporated above before source implementation. First unit native keys and non-null columns are database-enforced; allowed command/preference/reason values and positive revisions are service boundary invariants. No generic API can bypass that owner. This unit adds no separate bootstrap DDL installer. All later editor/API/delivery work remains required.

Implementation refinement before tests. Suppression precedence uses one conditional native UPSERT rather than insert-ignore followed by a separate lock/update. The UPSERT holds the conflicting row through the transaction, preventing a concurrent explicit resubscribe from deleting a user-suppression row in the gap before sticky suppression upgrades it. The conditional user-only DELETE remains. Both concurrent orders require real PostgreSQL proof. Source keys reserve the sticky: prefix within the160character bound.
