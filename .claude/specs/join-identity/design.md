# Private email proof owner

This internal slice supports email proof issuance, resend, consumption and fenced delivery for join_identity, email_login and profile_email. It adds no HTTP routes, account creation, JWT issuance or enabled signup capability. The approved participation account/join transaction, RSVP migration, phone proof, QR and newsletter UI/publication are later units. No live provider or shared database operation was used to build it.

`auth/services/join-identity.js` owns the actual outer mutation transaction. It refuses a foreign ambient Strapi transaction, takes one short PostgreSQL advisory identity lock, then locks intent/proof before account/mapping. Private helpers accept only its active transaction. SQLite uses its single writer. Participation will add the locked published event/garden checks and account/profile/RSVP/newsletter writes in this same outer transaction. The owner also awaits Knex executionPromise after the Strapi transaction resolves. Strapi5.36 can otherwise return its callback result when PostgreSQL rejects a deferred constraint at COMMIT. Network I/O and sessions stay outside the actual commit boundary. Existing legacy register/email writers still require paired cutover integration before new registration is enabled.

`join-identity-internal/proof-crypto.js` binds purpose, receipt, generation, destination and browser to code HMAC and AES-GCM payload. Destination, browser, network, request and payload keys have separate versioned derivation labels. `contact-value.js` preserves raw email and derives a separate delivery value by trimming surrounding whitespace and folding the domain only. Local case, dots and plus aliases remain distinct. This first validator supports common ASCII dot-atom addresses, not quoted/international mailboxes. The existing native user.add was exercised without unverified legacy contact fields or activeGarden; it rolls back and sends no welcome email. That probe is not the selected account construction. New accounts still require the verified delivery email; raw profile fields must not be truncated into legacy user.email.

The owner persists a non-secret key fingerprint in private Strapi core-store under its identity lock and transaction. A changed key, malformed/duplicate marker, or missing marker with existing proof/contact records refuses mutation. It never adopts a new key for an existing namespace. Keep the configured key and marker together; rotation needs an explicit migration. Ordinary public reads and old startup do not initialize this disabled owner.

Accepted proof issue/resend commands use the existing private participation-request ledger, with nullable destination/browser/network HMAC lookup fields and created-at indexes. Exact request HMAC replay precedes quota/cooldown. Destination limits are5/hour10/day, browser10/hour20/day and actual socket network500/hour2000/day. No raw IP or forwarded header is stored. Rejected issuance rolls back all provisional rows and creates no rejected ledger entry; its UUID may later be admitted. Accepted UUIDs are immutable and retain their replay receipt for seven days, independently of the one-day rate window. Failed-code verification returns inside the transaction so its five-attempt limit commits. Resend requires60seconds since issuance, cannot rewrite consumed proof, and creates a new generation without resetting history.

Requests bind purpose/intent/browser/actor and use UUIDs. Existing accepted intent/request must be resolved before provisional intent insertion. A join proof can only be used while its exact intent is pending and unexpired. Consume, wrong-attempt and delivery-claim writes enforce proof and intent expiry using database wall time after awaited locks. Resend may renew an expired code but still requires its exact parent intent live at the write. A resend receipt binds its original generation and scope; an old receipt cannot send a newer code. Unknown/unmapped/blocked login requests have the same pending public shape and no account creation or deliverable payload. A login proof rechecks its original active registry actor when consumed. This is proof evidence, not a completed session endpoint.

After issue commits, `deliverEmailProof` claims its original unconsumed, unexpired, unsuperseded pending generation once. It persists queued/attempt identity and erases sealed payload while capturing it in memory, then sends through the existing email plugin outside the transaction. Final recording requires the same generation and attempt. Real acknowledgement is accepted, dry-run simulated, ambiguous failure unknown. No queued/unknown attempt is automatically retried. Explicit resend supersedes an in-flight old code; a late acknowledgement cannot overwrite the new generation. Bounded expiry cleanup clears sealed payloads without a GET mutation.

The separate optional SMS dispatchGuard is already implemented and reviewed. It snapshots its function/presence at entry and requires exact true immediately before transport. Existing beforeSend remains intentional best-effort bookkeeping. Future phone/follow-up sends must use the metered send/sendSms boundary with dispatchGuard after the shared destination STOP owner is integrated; handleSms does not forward it automatically.

Tests exercise actual Strapi persistence and mocked external email only. They cover transaction ownership, raw preservation, admission/replay, zero-write rejection, generation/intent expiry fences, bounded committed guesses, single consumption, ownership/newsletter rollback, post-commit delivery, late acknowledgement, unknown outcomes, minimal user.add and key continuity. PostgreSQL independent-connection, commit-failure and restart checks, full required pipeline and final independent review gate this slice before any checkpoint PR or activation. Local evidence is tracked per unit, not inferred from this design.


Private account composition now follows a freshly consumed join proof inside the exact identity transaction. The owner tracks fresh claims per transaction; a previous transaction or a second resolution cannot reuse one. The internal accounts module resolves the current verified registry owner, conservatively scans legacy email in bounded pages, or creates a minimal local account with generated credentials, verified delivery email and authenticated role. It sets no active garden, membership, inferred name or phone credential. Legacy exact matches require their original account sign-in and browser-bound resume; ambiguous local-case or duplicate candidates fail closed. The intent, account, registry and create-only automatic newsletter handoff share one actual commit. Account resolution alone does not complete event registration or create a session.

Supported ASCII delivery mailboxes are bounded at254 characters, separately from the unchanged320 raw input bound. This fits native user.email without truncation and follows [RFC5321 path limits](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.1.3). Local case, dots and plus aliases remain distinct. Legacy register/contact writers still need paired migration to this identity lock before public signup activation. No controller or public capability is added by this private account slice.
