# Approved registration, QR attendance and follow-up contract, revision 2

The user approved implementation on October25,2026 after correcting phone to required and newsletter enrollment to automatic for account holders. This reconciled revision supersedes those two product rules in the immutable earlier proposal. Public reads remain approved and pushed. Implementation of private records, account creation, RSVP, attendance and outreach is authorized. Deployment and live sends remain off. Buddy is canceled.

## Chosen shape

Use one participation service for the complete event/account relationship. Keep pending identity proof and reusable profile private. Store RSVP, check-in and one follow-up as separate states on one participation record. Newsletter has a separate owner. A browser calls one operation and receives its actual outcome.

Candidate A is the base. Both candidates scored12/15 in the independent review. Take B's complete caller migration, verification inside page three, conservative legacy-account binding, scoped photo-card capability and publisher gate. Reject separate attendance and general queue services for this single follow-up. Retain explicit consent and delivery-attempt records. The alternative candidates are design evidence, not additional contracts. Only the routes and policies below enter the selected first release.

Use normal Strapi numeric primary keys and documentId, with a separate opaque receipt ID where needed. Do not introduce custom UUID primary keys. PostgreSQL migrations must create and verify actual compound unique constraints. The account probe proved outer transaction rollback works with the installed user service. It also proved fresh user tables allow duplicate emails and usernames. Metadata and prechecks cannot establish identity ownership.

## User behavior and proposed defaults

Get involved opens real Schedule discovery. The person chooses an actual future event before its existing RSVP modal opens. No sample event is assigned. The same modal becomes Your details, Your garden life, Review & updates. Verification stays within page three. Preferred name, email and phone are required. Interests, skills, availability and private access request are optional. Phone collection alone does not verify a destination or grant general SMS enrollment. All typed strings persist verbatim. Separate derived delivery values never replace them.

Returning people sign in before loading their own profile. They choose whether to reuse it. Account authentication remains separate from event registration. Back, edit, skip and recoverable errors preserve the draft. A saved-profile version conflict does not undo a valid RSVP. Event/account changes invalidate stale results.

Only confirmed or already_confirmed from the server means You're going. A requested or accepted verification email remains pending. RSVP is independent of a confirmation message's delivery. Check-in means an authenticated person pressed Check in with the event's current QR. It does not claim physical presence.

SMS follow-up starts unchecked. An unchecked new form leaves an existing SMS choice unchanged. Turning an existing choice off requires an explicit preference action. Newsletter enrollment is automatic for account holders and disclosed in account creation, with no separate newsletter opt-in checkbox. Prior newsletter unsubscribe/suppression stays authoritative. Use one app-owned newsletter subscription owner, backed by the existing Resend stack, instead of inferring enrollment from a delivered email or calling the legacy Mailchimp helper. The newsletter unit owns its coherent storage, automatic account handoff and unsubscribe contract. Do not silently backfill an audience or claim sending is enabled before sender configuration. This first contract implements the event-scoped photo/next-event follow-up. The existing prototype event-reminder checkbox and delivery promise stay deferred until an actual reminder schedule/job contract is selected. Do not render a working reminder checkbox backed only by a receipt. Event reminders remain an open requirement, not a completed feature. The follow-up choice is explicit at check-in. A separate reminder category cannot reuse it. A prior STOP remains authoritative. START does not resurrect an old grant. Joining or checking in never joins the garden's general SMS audience.

The proposed QR window starts30minutes before the event and ends at an organizer-entered close, at most12hours later and within that Pacific day. The organizer chooses Sunday18:00 or Monday09:00 for the follow-up. If Sunday18:00 has passed at check-in, use Monday09:00. Quiet hours are20:00 through09:00. Cancel unsent work after Monday12:00. Non-Sunday automation is outside this first contract. The timezone is America/Los_Angeles, converted by target calendar date rather than fixed-hour addition.

A photo requires the actual garden manager's rights/likeness permission record tied to its file version. A gallery entry alone is insufficient. The default is an SMS link to a token-scoped photo card and a real next eligible Sunday event at the same garden. No next event or approved photo means no follow-up. MMS is an explicitly selected organizer mode and uses existing metering. Neither accepted MMS nor downloaded copies can be recalled.

Proposed retention is24hours for unverified drafts,30days after the event for private access text,90days for detailed delivery diagnostics and24months for minimized consent evidence. RSVP/attendance deletion follows the account-deletion policy and needs an explicit retention review before launch. These are proposed product policies, not legal conclusions.

## Private storage and ownership

Each collection has draftAndPublish:false, no generic core API router and no broad role grants. Sensitive attributes are private as defense in depth. Custom services build exact output objects. Event/garden references use stable document identities.

- join_intents owns event, exact bounded draft, browser-secret hash, request ID/HMAC, state, expiry and completed receipt. Unique browser-secret/request ID. No contact lookup endpoint.
- contact_proofs owns purpose, intent or verified actor, raw and derived destination, destination HMAC, code hash, generation, attempts, expiry/consumption and sealed pending delivery payload. The proposed email code has8digits,10minute expiry, five attempts and one resend per minute. Existing six-digit SMS login keeps its contract. A proof cannot authorize another purpose or reveal a profile.
- verified_contacts owns channel/destination-HMAC and verified account binding. A real unique index and locked resolution prevent duplicate creation. Legacy collisions fail closed. A legacy account without an owned mapping requires existing sign-in after proof. Never select the first matching user or merge accounts automatically.
- join_profiles owns one record per user, raw name/email/phone, versioned optional preferences, contact-proof references and revision. It contains neither event access text nor outreach booleans.
- participations owns one unique event-documentId/user pair, RSVP state/time, event snapshot/access text, check-in time/token generation and one embedded follow-up state/due/deadline/receipt/attempt/SID/version. RSVP never sets attendance. A repeated check-in cannot create another logical follow-up.
- consent_receipts owns immutable actor, exact event/category, grant/revoke, displayed text version/hash, verified destination, source and server time. Requests have a unique source key. Jobs reference a particular receipt. Shared-number STOP is tracked by sms_destination_states with a suppression epoch so another account or a later START cannot revive old consent.
- event_participation_settings owns explicit window, current QR hash/generation/expiry, enabled/paused state, slot, mode and approved photo version/rights receipt. A start/garden/accessibility/publication/cancellation change invalidates the QR.
- participation_attempts owns fenced claim identity, preparing/dispatching/result, lease, request digest and provider SID. Commands use unique operation/actor/request keys and safe cached results. Same key with changed input conflicts. Never cache a JWT as an idempotency result.

All proof consumption, verified contact binding, account creation, participation, raw profile and requested receipt writes must share one database transaction. The tested user.add propagation is one prerequisite, not proof of this future complete operation. New constraints must survive Strapi restart and PostgreSQL concurrent tests before guest registration is enabled.

## Exact first-release API

All paths start with /api. JSON mutations carry requestId. JWT identity comes only from the server. Unknown fields, including userId, are rejected. Responses use {data:...} or {error:{code,message,fieldErrors}}. Syntax400, validation422, version/request conflict409, abuse429, invalid session401 and hidden/missing404. Private responses are no-store. Contacts, capabilities and bodies are excluded from logs.

- GET /participation/options is public and returns versioned preference groups, required-field policy and consent text. Real garden/interest IDs come from current records. There is one server-owned option catalog.
- GET and PUT /participation/me/profile require JWT. PUT accepts {requestId,version,preferredNameRaw,emailRaw,phoneRaw,preferences}. The response contains only that actor's saved profile and proof status. Saving a contact does not alter login credentials or grant outreach.
- POST /volunteer-days/:documentId/joins accepts optional validated JWT and {requestId,draft,browserSecret}. Anonymous requests require a random256bit browser secret. Return202 pending_verification with intent/expiry/send state, or200 confirmed/already_confirmed with safe event and own receipt. Visible closed events return409 unavailable. No full confirmed-user relation is returned. A valid proof resolving one legacy account without an owned mapping returns428 SIGN_IN_REQUIRED, not a completed join. The server retains the original intent, draft, proven destination and exact intended legacy account for a bound resume. Ambiguous matches fail closed without naming accounts.
- POST /join-intents/:id/resend accepts {requestId,browserSecret}. POST /join-intents/:id/verify accepts {requestId,browserSecret,code}. Verification is purpose/event/browser bound. It rechecks event eligibility, completes once and returns safe join outcome plus a session only after commit. Invalid/expired/superseded proof is400. Exact bound replay may recover the safe receipt; a spent code never becomes a general profile capability. A lost session response uses existing sign-in or fresh proof, never a cached JWT.
- POST /join-intents/:id/resume requires JWT and {requestId,browserSecret}. Only the exact server-bound legacy account may resume. Another actor returns409 ACCOUNT_CHANGED. Recheck current collisions, event eligibility and profile revision, then bind the proven contact and complete once. No second user or second proof is created.
- POST /auth/email-login/request accepts {requestId,emailRaw,browserSecret} and resolves only the verified-contact registry, never a typed-contact user-table match. Known, unknown, unmapped, blocked and capped contacts receive an indistinguishable202 pending shape. It creates no account. POST /auth/email-login/verify accepts {requestId,proofId,browserSecret,code}. Atomic consumption and a fresh eligible owned registry binding return only {jwt,user:{id,username,role:{id,name,type}}}. Invalid proof is generic400. This supports email-only accounts without a future event. New users recover a lost first session through a fresh email proof, not a cached session. Legacy sign-in remains existing SMS or password login before intent resume. No general password-reset contract is added.
- GET /volunteer-days/:documentId/joins/me requires JWT and returns null or the own receipt. GET /participation/me?page=1&pageSize=100 returns the actor's stable event identities/state for Schedule. Neither exposes private snapshots or grants access to hidden events.
- POST /participation/me/contact-proofs and POST /participation/me/contact-proofs/:id/verify require JWT. Bodies are {requestId,channel,rawValue,purpose,browserSecret} and {requestId,code,browserSecret}. Proof belongs to the current actor and exact destination. Prior STOP blocks SMS proof rather than bypassing suppression.
- POST /participation/me/consents requires JWT and {requestId,eventDocumentId,choice}. A grant requires an owned verified phone proof; missing proof is422 for this separate outreach-only operation and never reverses attendance. It records the explicit fresh choice and may plan the same already-attended unplanned follow-up once before its deadline. Check-in with an unverified optional choice returns pending_proof with attendance committed and no effective grant. Later phone proof alone grants nothing; the person deliberately submits this consent command.
- POST /participation/me/consents/:receiptId/revoke requires JWT and {requestId}. It appends withdrawal and cancels not-dispatched work for that receipt. It changes no other channel.
- GET /check-ins/:token is read-only and returns safe event/window/login requirement and optional own receipt. POST requires JWT and {requestId,followupChoice}. First valid check-in returns201, repeat returns200, closed window409 and invalid/revoked token404. Declining texts never blocks attendance. GET/HEAD/link preview never changes state.
- GET and PUT /volunteer-days/:documentId/participation/manage require that garden's manager or established Administrator. PUT accepts {requestId,version,opensAt,closesAt,enabled,paused,followupSlot,format}. It re-plans only eligible undispatched work. GET exposes settings and aggregate counts, no public roster.
- POST /volunteer-days/:documentId/participation/qr/rotate requires the same manager and {requestId,version}. It returns a new token URL once and invalidates its predecessor. Lost response requires explicit new rotation, not a GET mutation.
- POST /volunteer-days/:documentId/participation/photo and /photo/revoke require the same manager, {requestId,version,mediaId,mediaVersion,rightsConfirmed,rightsNote}. Server stamps approval identity/time and validates that media belongs to this event.
- GET /volunteer-days/:documentId/participants is manager-only, bounded pagination and minimum event roster/access-request fields. Contact inclusion requires the explicit manager projection. No arbitrary populate or general profile search.
- GET /photo-cards/:token returns only that approved photo version and real public event links, never a recipient identity. The separate hashed capability expires30days after the event. Revocation returns404. It is separate from QR and proof tokens.

An event must be published, Public, not canceled/disabled, associated with a published garden and future at join and proof completion. The recent-past public feed is not the write policy. Check-in uses its explicit window and current settings. Organization-only/external-RSVP events keep their existing external behavior in this first release.

## Canonical first-release appendix

This appendix completes the selected contract. Candidate field lists are not implementation authority. Every new collection uses native numeric id/documentId. Opaque public receipt IDs are separate unique random values. All fields below are private unless included in an explicit projection. UTC timestamp is the storage type. Required fields are non-null. A field marked optional may be null. Mutation request IDs are UUID strings. Check constraints and compound/partial uniqueness are real PostgreSQL migrations, verified again after a Strapi restart.

Caller usage is `eventStore.submitJoin(eventDocumentId, draft, requestId)` then apply the returned outcome only if actor/event/request generations still match. `eventStore.readOwnProfile()` takes no contact search key. `participationStore.checkIn(token, followupChoice, requestId)` completes attendance and its optional plan in one command. Neither browser coordinates account creation, consent writes and queue insertion.

Selected backend modules are src/api/participation/services/participation.js and thin custom controller/routes beside it. That service owns profiles, intents, participation, settings, receipts, attempts and command results. Private persistence stays inside its participation-internal directory. src/api/auth/services/join-identity.js and custom controller/routes own proof and verified-contact resolution. Existing sms.js/transport.js retain metering and transport, with the new mandatory fail-closed guard. src/utils/sms-opt-out.js owns the global STOP integration. config/cron-tasks.js invokes only `participation.deliverDue({now,limit})` behind its separate disabled flag. No bootstrap send runs.

The not-implemented signatures are `submit(actorOrGuest,eventId,draft,requestIdentity) -> JoinOutcome`, `completeProof(proofSubmission,requestIdentity) -> ProofOutcome`, `resume(actor,intentId,browserSecret,requestIdentity) -> JoinOutcome`, `readOwnProfile(actor) -> Profile|null`, `saveOwnProfile(actor,edit,version) -> Profile`, `checkIn(actor,token,choice,requestIdentity) -> CheckInOutcome`, `manage(actor,eventId,command) -> ManagerOutcome`, and `deliverDue({now,limit}) -> DeliveryCounts`. A grant needs an owned proof for the exact destination and purpose, plus the displayed consent text. JWT alone, user.phoneNumber, absence of STOP and email identity proof do not prove a new phone. The first-release JoinDraft accepts no follow-up grant. That choice occurs only at check-in or the explicit later consent command. Optional unverified check-in choices are browser-memory drafts only, expire after24hours and clear on reload/logout. They authorize no send, persist no effective receipt and report choiceResult:pending_proof. The authoritative server delivery state remains not_planned or its actual existing state. Pending phone choice is not a delivery state. Off makes no SMS proof request. Changing raw contact clears its profile proof association. A deliberate later proof/choice may plan the same already-attended unplanned follow-up once, within its deadline, without another check-in. It rechecks actor, destination, text version, consent and STOP. It never revives canceled, accepted or unknown work. RSVP and attendance succeed while optional outreach is blocked. A stale profile version returns profileSave:conflict while retaining the committed event snapshot.

Bounds are name120characters with visible content, email320, phone80, access text2000, at most30distinct known IDs per preference array and16KiB total body. Validation rejects invalid input without rewriting raw values. The versioned server catalog supplies all preference/text IDs. A safe event projection is only documentId, title, startDatetime, eventPath and garden documentId/title/slug. A self profile contains only its raw fields, preferences, proof status and version. A manager roster is event-scoped preferred name, own submitted contact fields only when explicitly requested, access request, RSVP/check-in times and receipt ID. No public receipt contains another actor or access text.

The chosen email derivation version1 removes surrounding whitespace only in a separate delivery value, preserves the local part, folds the domain and rejects unsupported syntax. It preserves plus aliases and dots. All proof, registry, collision and delivery paths use that same version. Legacy collision preflight also flags case-folded ambiguities instead of merging them. Phone derives a separately validated E.164 value. Raw strings remain verbatim. Destination keys are HMACs over channel/version/derived value. Code digests are keyed HMACs over proof identity, generation, purpose and code with a separate versioned server secret. An unkeyed code hash is forbidden.

Proof purposes are join_identity, email_login, profile_email and profile_phone. Issuance and completion bind actor/intent, original browser and exact destination. Attempts increment and consume under one transaction lock. Initial requests and resends share proposed destination and browser/IP limits of5per hour and10per day, plus60seconds between sends. Unknown/blocked/capped email-login requests retain the same public shape. Resend supersedes the old generation without resetting aggregate budgets. Sealed delivery payload is erased after acceptance, unknown outcome or expiry. Code, browser secret and capability values never enter logs. These controls do not enable live delivery.
